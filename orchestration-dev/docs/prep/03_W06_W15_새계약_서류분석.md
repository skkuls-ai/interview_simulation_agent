# W-06 · W-15. 새 계약(docs/04) 기준 서류 분석

> 담당: A · 브랜치: `feature/interview-prep` · 2026-09-30
> docs 작업: W-06 분석 프롬프트 초안, W-15 샘플 4종으로 `Analysis` 실제 생성

## 왜 새로 만들었나

어제까지의 분석 코드(`backend/interview/llm_analysis_agents.py`)는 담당 3의 이전 구조(`InterviewBlueprint`)에 맞춰져 있었습니다. 팀 docs가 정한 **새 계약**은 결과 양식이 다릅니다 (`Requirement` / `Claim` / `Checkpoint` / `RequirementLink`). B(질문 생성), E(피드백), 화면 7(연결 정보)이 이 양식을 받으므로, 새 계약 기준으로 다시 만들었습니다.

- C의 `schemas/`가 아직 올라오지 않아, docs 계약 모델을 **글자 그대로 복사한 임시 파일**(`contract.py`)로 개발했습니다.
- 담당 3의 이전 구조에 의존하지 않는 **독립 폴더**라, C의 저장소 뼈대가 올라오면 `backend/app/nodes/prep/`로 옮기고 import만 바꾸면 됩니다.
- 어제 방식(원문 그대로 복사 → 코드가 검증, ID는 코드가 발급)은 그대로 가져왔습니다.

## 파이프라인 (docs/05 준비 파이프라인 1~4단계)

```text
read_posting  채용공고 ─┐ (LLM, 문서별로 따로 · 동시 실행)
              직무기술서 ┘→ Requirement (RQ-, SKILL / DUTY / TALENT)
read_resume   이력서·자소서 → Claim (CL-, 원문 그대로, 유형 7종)     ← read_posting 과 동시 실행
link          Requirement ↔ Claim → RequirementLink (요구사항마다 1개, 비어 있으면 "서류에 근거 없음")
checkpoints   Claim → Checkpoint (CP-, 중요한 순서, 최대 8개)
```

- **채용공고와 직무기술서를 따로 분석합니다.** 어제는 한 번에 넣어서 항목이 30개를 넘자 뒷부분이 잘렸습니다.
- `run_analysis(llm, 서류 4종, on_step)`: C가 통째로 부르면 되고, `on_step(step_id, state, detail)` 콜백으로 화면 3의 단계 진행을 기록할 수 있습니다. 1·2단계 완료 문구도 코드가 만듭니다 (`요구사항 n개 확인`, `경험 n개, 확인할 주장 n개`).
- 단계별 함수(`read_postings`, `read_resume`, `link`, `checkpoints`)를 C가 그래프 노드로 하나씩 연결해도 됩니다.

## 프롬프트 원칙

| 원칙 | 적용 |
|---|---|
| 원문 그대로 복사 | 요구사항 인용, 주장 문장. 코드가 원문과 대조하고 없으면 버림 |
| ID는 코드가 발급 | LLM은 연결·검증 포인트 단계에서 이미 발급된 ID를 참조만 함 |
| 판단 금지 | "거짓", "과장" 같은 표현 금지. 확인할 점만 다룸 |
| 서류별로 따로 | 이력서와 자소서의 주장을 합치지 않음 (서류 간 불일치를 남기기 위해) |
| 불일치 오탐 방지 | 포함 관계(본인 포함 인원), 표현 차이, 한 서류에만 있는 내용은 불일치가 아님 |

## 코드 안전장치 (docs/05 책임 경계)

| 대상 | 규칙 |
|---|---|
| 요구사항 | 원문에 인용이 없으면 제외, 같은 위치·같은 요약 중복 제거, 문서당 최대 20개 |
| 주장 | 원문에 없으면 제외, 서류 구분만 틀렸으면 정정, **원문 글자로 저장**, 같은 위치 중복 제거, 유형이 없으면 제외, 최대 30개 |
| 연결 | 없는 요구사항·주장 ID 제거, **요구사항마다 정확히 하나씩** (빠진 요구사항은 "근거 없음"으로 채움) |
| 검증 포인트 | 없는 주장 ID 제거, 근거 주장이 하나도 없으면 제외, 같은 주장 묶음 중복 제거, **중요도 순 정렬**(질문 생성이 앞에서부터 쓰도록), 최대 8개 |
| LLM 실패 | 단계별 규칙 기반 대체값 (글머리표 줄 → 요구사항, 수치·역할 단서 문장 → 주장, 영문 기술 용어 겹침 → 연결, 주장 유형 → 검증 포인트). LLM 없이도 계약 모양의 `Analysis`가 나옴 |

계약에 없는 정보(주장이 속한 경험 이름, 요구사항 원문 구절, 검증 포인트 우선순위)는 `AnalysisReport`에만 두고 `Analysis`에는 넣지 않습니다.

### 1회차에서 찾아 고친 것

| 관찰 | 원인 | 고친 원칙 (프롬프트) |
|---|---|---|
| G2 "로그 수집과 응답 품질 모니터링" 공백을 못 잡음 | 직무기술서 한 줄의 "API 개발, 로그 수집과 응답 품질 모니터링"을 요구사항 하나로 합쳐서 API 경험 때문에 연결됨 | 한 줄에 서로 다른 요구가 여러 개면 **요구마다 나누기** |
| CP4(주도한 역할), CP5(Send 설계) 놓침 | 이력서의 단순 작업 나열에 검증 포인트를 씀 | 자기소개서에서 **강하게 내세운 주장(주도, 설계, 결정, 효과)을 우선**, 유형을 골고루 |
| 주장 27개로 많음 | 이력서 제목 줄마다 주장으로 뽑음 | 제목 줄은 **본인 역할이 적혀 있을 때만** 주장 |

정답 라벨에만 맞추지 않도록, 특정 문장이 아니라 **실제 서류에도 통하는 일반 원칙**으로 고쳤습니다.

### 남은 한계

- **CP7(스키마 합의 효과, low)은 여전히 놓칩니다.** 우선순위가 낮은 항목이라 허용 범위로 봅니다.
- **채점이 느슨한 부분:** CP5는 "리드 및 기여도" 검증 포인트 하나에 CP4와 함께 묶여 탐지됐습니다. 자동 채점은 "근거 주장을 참조하는가"만 보므로, 확인할 내용의 방향은 사람이 결과를 읽고 확인해야 합니다.
- **요구사항을 나누다 짧은 조각이 버려질 수 있습니다.** 2회차에 "문서 수집·전처리"(공백 제외 7자)가 8자 기준에 걸려 제외됐습니다. 같은 줄의 나머지 요구는 남았습니다.
- **LLM 결과는 실행마다 달라집니다.** 2회 실행 결과이므로, 발표 전에 여러 번 돌려 평균과 편차를 확인해야 합니다.
