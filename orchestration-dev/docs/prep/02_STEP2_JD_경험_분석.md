# STEP 2. JD 분석과 경험 분석 LLM 구현

> 담당: 담당 1 · 브랜치: `feature/interview-prep`

## 만든 것

| 파일 | 내용 |
|---|---|
| `backend/interview/quotes.py` | 원문 인용 검증 (분석·평가 단계 공용) |
| `backend/interview/prompts/analysis.py` | JD 분석, 경험 분석의 LLM 출력 모델과 프롬프트 |
| `backend/interview/llm_analysis_agents.py` | `LLMAnalysisAgents`: `analyze_jd`, `analyze_experiences`를 LLM으로 구현. 나머지 6개 메서드는 스텁 상속 |
| `tests/test_prep_quotes.py` | 인용 검증 규칙 테스트 8개 |
| `tests/test_prep_llm_analysis.py` | 가짜 LLM으로 안전장치·대체·그래프 전체 실행 테스트 11개 |
| `scripts/prep_smoke.py` | 데모 샘플로 실제 Gemini 호출 (pytest 밖, 할당량 사용) |

## 설계

```text
서류 ──> LLM (구조화 출력) ──> 코드 안전장치 ──> Blueprint 모델 (JDRequirement, Experience)
                                   │
                                   └─ 실패하거나 남은 항목이 없으면 → 스텁 결과로 대체
```

### LLM 출력 모델과 Blueprint 모델을 분리한 이유

- LLM 출력 모델에는 **원문 인용(`source_quote`)** 칸이 있고, **ID 칸이 없습니다.**
- 인용은 코드 검증에만 쓰고, ID는 코드가 붙입니다.
- Blueprint 스키마(담당 3)는 바꾸지 않았습니다. 인용 필드 추가는 담당 3과 합의 후 진행합니다.

### 원문 인용 검증 규칙 (`quotes.py`)

| 규칙 | 이유 |
|---|---|
| 공백·줄바꿈·문장부호를 지우고 비교 | LLM이 문장부호를 붙이거나 빼고, STT 원문에는 문장부호가 거의 없음 |
| 공백·문장부호 제외 **8자 미만은 거부** | 짧은 구절은 우연히 일치하거나 여러 곳에 있어 가리키는 곳이 모호함 |
| **유사 매칭 금지** | "30%"를 "50%"로 바꾼 인용이 통과하면 안 됨 |
| 위치는 코드가 다시 계산 | LLM이 준 위치는 믿지 않음 |
| 끝의 닫는 괄호·따옴표 보정 | "(986개 인덱싱"처럼 괄호가 한쪽만 남지 않게 |

### 코드 안전장치

| 대상 | 규칙 |
|---|---|
| 요구사항 | 공고에 인용이 없으면 제외 (섹션 제목, 지어낸 요구사항 차단), 같은 위치·같은 요약은 중복 제거, 최대 20개 |
| 회사명·직무명 | 공고에 실제로 있을 때만 사용 |
| 경험 | 해당 서류에 인용이 없으면 제외. 서류 구분만 틀렸으면(이력서 ↔ 자소서) 정정 |
| 주장 구절(`claimed_results`) | 원문에서 찾은 것만, **LLM이 옮긴 글자가 아니라 원문 글자로** 저장. 중복 제거, 경험당 최대 6개 |
| 역량 코드 | 문항 은행 30개에 있는 것만 (영역 코드 `leadership` 등은 제거) |
| ID | `R1`, `E1`…을 코드가 순서대로 부여 |
| 실패 | LLM 오류, 유효 항목 0개 → 스텁 결과로 대체하고 사유 기록 |

### 경험 분석 핵심 결정

- **서류별로 따로 추출합니다.** 같은 프로젝트라도 이력서와 자소서의 경험을 합치지 않아야 "1,000개 ↔ 약 5,000개" 같은 불일치(L2)가 다음 단계까지 남습니다.
- **주장 구절을 원문 그대로 저장합니다.** STEP 3의 `verification_points()`는 원문 서류를 받지 않으므로, 여기서 검증된 원문 구절이 검증 포인트의 근거가 됩니다.

## 결과 (데모 샘플, 실제 Gemini)

모델: `gemini-3.8-flash` (AI Studio 키)

| 항목 | 스텁 (기준선) | LLM |
|---|---|---|
| 요구사항 | 8개, **제목 줄을 요구사항으로 착각** | **16개**, 제목 줄 0개. 담당 업무 4, 자격 5, 우대 4, 인재상 3 |
| 필수/우대 구분 | 줄 순서로 앞 3개만 must | 공고 섹션대로 정확히 구분 |
| 경험 | 10개 (서류 줄마다 1개) | **7개** (이력서 4, 자소서 3, 프로젝트 단위) |
| 주장 구절 | 0개 | 경험마다 원문 구절 |
| 정답 라벨의 서류 인용 포착 | 0 / 7 | **7 / 7** |
| JD 공백 라벨 (L8, L9) | 없음 | R9, R12로 추출됨 (공백 판정은 STEP 3) |
| 소요 시간 | - | JD 약 7초, 경험 약 10~15초. 동시 실행이라 합계 약 10~15초 |

### 개선 과정 (smoke test 3회)

| 회차 | 관찰 | 조치 |
|---|---|---|
| 1 | 요구사항 12개 상한에 걸려 인재상 3개가 잘림. 인재상은 역량 질문 선정에 쓰임 | 상한 12 → 20 |
| 1 | "(986개 인덱싱"처럼 닫는 괄호가 잘림 | 인용 끝 닫는 기호 보정 |
| 1~2 | L4 "4인 팀, 팀 리드" 미포착. 2회차에 LLM이 뽑았지만 **8자 미만이라 코드가 거부** | 기준을 낮추지 않고, 제목 줄 전체를 복사하도록 프롬프트 수정 |
| 3 | 서류 라벨 7/7 포착, 안전장치 발동 0건 | - |

**2회차의 거부는 안전장치가 의도대로 동작한 사례입니다.** "4인 팀"은 이력서에 세 번 나와서 짧은 인용으로는 어느 프로젝트인지 알 수 없습니다.

## 테스트

```bash
cd orchestration-dev
INTERVIEW_USE_LLM=0 .venv/bin/python -m pytest -q tests -p no:warnings   # 124 passed (API 호출 없음)
.venv/bin/python -m scripts.prep_smoke                                    # 실제 Gemini 호출
```

**가짜 LLM 테스트가 확인하는 것**
- 지어낸 요구사항, 섹션 제목, 없는 역량 코드 제거
- 공고에 없는 회사명 제거
- 숫자를 바꾼 주장 구절 제거
- 서류 구분 정정, 지어낸 경험 제거
- LLM 오류 시 스텁 대체
- 서류가 없으면 LLM을 호출하지 않음
- 분석 그래프 전체가 끝까지 실행됨

## 남은 과제

- 경험 분석이 가장 오래 걸립니다(10~15초). 준비 시간 목표(20~40초) 안이지만, STEP 3~5 호출이 더해지면 다시 측정합니다.
- `google-genai`의 AFC 경고 로그가 출력됩니다. 담당 3의 클라이언트 설정 문제로, 동작에는 영향이 없습니다.
