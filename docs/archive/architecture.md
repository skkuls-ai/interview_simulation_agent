# 멀티 에이전트 면접 시뮬레이터 아키텍처

> **보관용 문서 (9/28 풀스펙 설계).** MVP 최소 기능 기준의 현재 아키텍처는 [05-architecture.md](../05-architecture.md)를 본다. 이 문서는 MVP 이후 확장(150문항 은행, 꼬리질문, 평가자 3명 패널, CHRO 규칙 판정, 이어하기 등)을 다시 검토할 때 참고한다.
> 아래 그림·`screen_flow.md` 링크는 원본 파일이 저장소에 없어 연결되지 않는다.

기준: `feature/orchestration`, 2026년 9월 29일
그림: [architecture.png](architecture.png) (원본 `architecture.svg`, 생성 스크립트 `make_architecture_diagram.py`)

## 1. 한눈에 보기

- 질문 은행 150문항(역량 4영역)을 바탕으로, 지원 서류가 있으면 개인화하고 없으면 은행 문항 그대로 면접을 진행합니다.
- 면접 흐름은 LangGraph 그래프 두 개가 맡습니다.
  - **분석 그래프**: 면접 전 한 번 실행해 면접 설계도(`InterviewBlueprint`)를 만듭니다.
  - **면접 그래프**: 설계도를 받아 질문, 꼬리질문, 판정, 피드백까지 진행합니다. 사용자 입력이 필요한 곳마다 멈추고(interrupt) 체크포인트를 저장하므로 중단 후 재개할 수 있습니다.
- 문항별 채점은 그래프 밖 **세션 서비스**가 백그라운드로 돌립니다. 면접 진행 속도는 채점 시간에 영향을 받지 않습니다.
- 합격, 보류, 불합격 판정(CHRO)은 LLM이 아니라 **규칙**으로 정합니다.

| 구분 | 사용 기술 |
|---|---|
| 그래프, 상태 | LangGraph (StateGraph, interrupt, SqliteSaver 체크포인트) |
| API | FastAPI (REST, WebSocket은 예정) |
| LLM | Gemini on Vertex AI (학교 GCP 프로젝트, ADC 인증, google-genai) |
| 저장소 | SQLite + 파일 (`var/`) |
| 화면 | React (예정), 흐름은 [screen_flow.md](screen_flow.md) |
| 음성 | 받아쓰기 3.5 Transcribe Live, 음성 합성 3.1 Flash TTS (대체 2.5 Flash TTS) (예정) |
| 표정, 시선 | MediaPipe, 팀원 `feature/perception` 모듈 (연동 예정) |

LangChain은 쓰지 않습니다. 모델 호출은 google-genai로 직접 하고, 구조화 출력은 JSON 스키마로 강제합니다.

## 2. 구성 요소

| 구성 요소 | 위치 | 역할 |
|---|---|---|
| 브라우저 | `frontend/` (예정) | 모든 화면을 백엔드가 준 `prompt.type` 하나로 결정. 타이머와 장치만 직접 관리 |
| FastAPI | `backend/api/` | 세션, 문서, 분석, 시작, 행동, 재개, 결과 엔드포인트. `/health`, CORS, 오류 코드 매핑(400/422/503) |
| 세션 서비스 | `backend/service/session_service.py` | 동의 확인, 문서 저장, 그래프 실행과 재개, 백그라운드 평가 제출, 결과 저장, 24시간 지난 세션 정리 |
| 분석 그래프 | `backend/interview/analysis_graph.py` | JD, 경험 분석부터 면접 설계도까지 |

| 평가 패널 | `backend/interview/evaluation.py` | 평가자 3명, 코드 검증, 검증 에이전트, 재평가, 중앙값 |
| LLM 클라이언트 | `backend/llm/` | 역할별 모델 설정, 재시도, 스키마 `$ref` 펼치기 |
| 질문 은행 | `backend/question_bank/` | 엑셀 → JSON 변환, 중복, 대체 문구 표시 |
| 저장소 | `backend/service/store.py`, `var/` | 세션, 평가, 체크포인트, 결과, 업로드 |

## 3. 사용자 흐름

1. 첫 화면: 새 면접, 이어하기, 이전 결과 보기
2. 개인정보 동의: 마이크 필수, 카메라, 문서, 결과 저장은 선택
3. 서류 업로드 (JD, 이력서, 자소서, 모두 선택). 없으면 문항 은행만으로 진행
4. AI 분석 (분석 그래프)
5. 면접 구성 안내: 주제, 문항 수, 예상 시간만 표시 (영역 이름과 질문 내용은 보여주지 않음)
6. 카메라, 마이크 점검
7. 준비시간: 사용자가 "면접 시작"을 누를 때까지. 여기서부터 답변 시간 측정
8. 자기소개 1분
9. 본 면접: 성과 → 관계 → 적응 → 리더십, 영역별 2문항, 근거가 부족하면 1문항 추가, 문항마다 꼬리질문 최대 3회
10. 마무리 질문 (항상 진행, 평가 미반영)
11. 결과 정리 → 종합 판정과 피드백 → 첫 화면

## 4. 분석 그래프

```
JD 분석 ─┐
         ├─> JD 경험 연결 ─> 검증 포인트 ─> 질문 계획 ─> 질문 검증 ─> 평가 기준 ─> 면접 설계도
경험 분석 ┘
```

| 노드 | 하는 일 | 상태 |
|---|---|---|
| JD 분석 | 요구사항, 회사 정보 추출 | 스텁 (LLM 예정) |
| 경험 분석 | 이력서, 자소서에서 경험 추출 | 스텁 |
| JD 경험 연결 | 요구사항별 강함, 부분, 공백 판단 | 스텁 |
| 검증 포인트 | 서류 기반 확인 필요 주장 생성. 영역 코드 유효성 검사 | 스텁 |
| 질문 계획 | 영역별 2문항 + 예비. 검증 포인트가 있는 역량 가산 | 완료 |
| 질문 검증 | 개인화 문구 검사, 실패 시 최대 2회 재시도 후 원본 문항으로 되돌림 (`validation: passed / reverted`) | 스텁 |
| 평가 기준 | 1~5점 척도 기본값 + JD 보조 기준, 자기소개 기준 | 스텁 |
| 면접 설계도 | 위 결과를 하나로 묶어 면접 그래프 입력으로 저장 | 완료 |

문서가 없으면 JD, 경험 관련 노드는 빈 결과를 내고 은행 문항을 그대로 씁니다.

## 5. 면접 그래프

⏸ 표시는 사용자 입력을 기다리며 멈추는 지점입니다.

```
준비시간⏸ ─> 자기소개⏸ ─> 자기소개 확인 ─> 본 질문 선택 ⇄ 답변 대기⏸ ⇄ 꼬리질문 판단
                                               │            └─ 무응답⏸
                                               └─(모든 영역 끝 또는 45분 초과)
                                                  ─> 마무리 질문⏸ ─> 평가 대기⏸ ─> 관찰자 ─> CHRO 판정 ─> 종합 피드백
```

| 노드 | 하는 일 |
|---|---|
| 준비시간 (`await_ready`) | 사용자가 시작할 때까지 대기 |
| 자기소개 확인 | 회사 관점(왜 이 회사인지, 포부, 경험 적합성)으로 확인. 서류에 없던 새 주장만 검증 포인트로 추가 |
| 본 질문 선택 | 영역 순서와 문항 수, 추가 문항, 45분 예산 판단. 영역 이름 없이 자연스러운 전환 문구 사용 |
| 답변 대기 (`await_answer`) | 준비 5초 후 답변. 1분 넘으면 경고와 초과 시간만 표시, 끊지 않음 |
| 무응답 (`no_response`) | "다시 답변하시겠어요?" 다시 답변 또는 넘어가기(본 질문이면 1점) |
| 꼬리질문 판단 | STAR 빈 요소 기준으로 꼬리질문 여부와 문구 결정. 최대 3회. 문항이 끝나면 품질 라벨 부여 |
| 마무리 질문 | 시간과 상관없이 항상 진행, 평가 미반영 |
| 평가 대기 (`await_evaluations`) | 세션 서비스가 모은 패널 결과 수신. 넘어간 문항은 1점 |
| 관찰자 | 음성, 영상 지표 해석 (현재 비언어는 판정 미반영) |
| CHRO 판정 | 규칙 기반 합격, 보류, 불합격 |
| 종합 피드백 | 역량별 개선점, 자기소개 피드백, 시간 관리, 다음 면접 대비, 품질 분포 |

### 품질 라벨

문항(스레드)이 닫힐 때 하나를 붙입니다.

| 라벨 | 의미 |
|---|---|
| SUFFICIENT | STAR 요소가 충분 |
| PARTIAL | 일부 요소 부족 (꼬리질문 한도에서 더 물어야 했던 경우 포함) |
| VAGUE | 구체성 부족 |
| OFF_TOPIC | 질문과 무관 |
| INCONSISTENT | 앞선 답변이나 서류와 모순 |

## 6. 에이전트와 모델

| 에이전트 | 모델, 사고 수준 | 호출 시점 | 상태 |
|---|---|---|---|
| 꼬리질문 판단 | Gemini 3.8 Flash, LOW, 8초 제한, 재시도 1 | 답변마다, 동기 | 구현 완료 (실패 시 규칙 기반 대체) |
| 평가자 × 3 | 3.8 Flash, MEDIUM | 문항 종료 시 백그라운드 | 구현 완료 |
| 검증 에이전트 | 3.7 Flash, MEDIUM (평가자와 다른 모델) | 평가자 출력 검사 | 구현 완료 |
| 자기소개 평가 | 3.8 Flash | 자기소개 후 백그라운드 | 구현 완료 |
| 자기소개 확인 | 3.8 Flash | 자기소개 직후 | 스텁 |
| 분석 에이전트들 | 3.8 Flash | 면접 전 1회 | 스텁 |
| 종합 피드백 | 3.8 Flash, HIGH | 면접 끝 | 스텁 |
| 관찰자 | 규칙 + 팀원 지표 | 면접 끝 | 스텁 |
| CHRO | 규칙 (LLM 없음) | 면접 끝 | 구현 완료 |

- 3.8 Flash는 temperature를 쓰지 않고 thinking_level(LOW, MEDIUM, HIGH)로 조절합니다.
- 역할별 모델은 `.env`의 `INTERVIEW_MODEL_<ROLE>`로 바꿀 수 있고, `INTERVIEW_USE_LLM`이 꺼져 있으면 모두 스텁으로 동작합니다.
- 백그라운드 호출은 동시 3개(`bg_llm_concurrency`)로 제한하고, 꼬리질문 판단은 이 제한을 거치지 않아 항상 먼저 처리됩니다.

## 7. 평가 패널 (문항마다, 그래프 밖)

1. 평가자 3명이 같은 기준으로 병렬 채점
2. 코드 검증: 인용 근거가 실제 답변에 있는지(유사도 0.85 이상), 체크포인트 방향, 형식
3. 검증 에이전트가 각 채점의 타당성 검토
4. 무효 평가자만 무효 이유를 넘겨 1회 재평가
5. 유효한 점수의 중앙값(반올림)으로 합침

| 결과 | 조건 |
|---|---|
| ok | 유효 평가자 2명 이상 |
| disputed | 유효 점수 차이 2점 이상 (점수는 확정, 화면에 의견 차이 표시) |
| undetermined (판단 보류) | 재평가 후에도 유효 평가자 1명 이하 |

- 대표 의견은 최종 점수와 같은 점수를 준 평가자의 것을 씁니다.
- 채점 제한 시간은 420초이며, 세션이 끝난 뒤 도착한 채점은 저장하지 않습니다.
- 자기소개는 평가자 1명이 회사 관점으로만 보고 합불에 반영하지 않습니다.

## 8. CHRO 판정 규칙

| 규칙 | 기본값 |
|---|---|
| 역량별 최저 (과락) | 한 역량이라도 평균 2.0 미만이면 불합격 |
| 전체 평균 | 3.0 기준. 3.3 초과 합격, 2.7 미만 불합격 |
| 보류 구간 | 평균이 기준 ±0.3 안(2.7~3.3)이면 보류 |
| 못 물은 영역 | 합격이면 보류로 낮춤 (설정으로 불합격 가능) |
| 상한 | INCONSISTENT 답변 또는 판단 보류 문항이 하나라도 있으면 최대 보류 |
| 평가 불성립 | 모든 문항이 판단 보류면 보류 (지원자 탓이 아니므로) |

모든 문항이 판단 보류면 평균, 과락 규칙은 "해당 없음"으로 표시합니다. 비언어 지표는 현재 판정에 넣지 않습니다. INCONSISTENT 답변은 피드백의 "다음 면접 대비"에도 "추가 질문을 받을 수 있다"는 안내로 나옵니다.

## 9. 시간 규칙

| 항목 | 값 |
|---|---|
| 준비시간 (문항마다) | 5초, 자기소개, 꼬리질문, 마무리 포함 |
| 답변 권장 시간 | 1분. 넘으면 경고와 초과 시간 표시, 끊지 않음 |
| 전체 예산 | 45분, 답변 시간만 합산 (준비, 대기 제외) |
| 예산 초과 | 남은 영역을 건너뛰고 마무리 질문으로 이동 |
| 피드백 | 장황했던 답변 목록과, 그 때문에 못 물은 영역(예: 리더십) 안내 |

## 10. 데이터와 개인정보

| 저장 항목 | 내용 | 보관 |
|---|---|---|
| sessions | 동의, 설정, 면접 설계도 | 세션 종료 또는 24시간 |
| evaluations | 문항별 채점 | 세션 종료 시 삭제 |
| checkpoints | 면접 State (재개용) | 세션 종료 시 삭제 |
| results | 최종 결과 | 결과 저장 동의 시에만 |
| uploads | 문서 원문 | 세션 종료 시 삭제 (최대 24시간) |

- 동의서 버전 `2026-09-28.2`, Google Cloud로 처리됨을 고지합니다.
- 영상 원본은 서버로 보내지 않고 표정, 시선 지표만 받습니다.
- 답변에는 질문 화면의 `sequence`를 붙여 같은 요청이 두 번 와도 한 번만 기록합니다.
- 일시 오류는 503으로 돌려주고, 같은 요청을 다시 보내면 멈춘 지점부터 이어서 처리합니다.

## 11. 안전장치

- 생성 질문 검사(`guards.py`): 채용절차법상 물을 수 없는 주제(신체, 출신 지역, 혼인, 가족, 재산, 종교, 정치 성향, 나이 등)를 정규식으로 차단. 한글 단어 경계를 따져 "시키는", "지식재산" 같은 오탐을 막습니다.
- 영역 이름 노출 금지: 질문과 전환 문구에 "성과역량", "리더십역량" 같은 영역 이름이 나오면 차단합니다.
- 꼬리질문 판단 실패(시간 초과, 형식 오류, 검사 실패) 시 규칙 기반 대체 문구로 진행합니다. 생성 질문은 120자, 물음표 2개까지 허용합니다.
- 모든 LLM 출력은 필수 필드를 모두 갖춘 JSON 스키마로 받습니다.

## 13. 결정 기록

| 결정 | 이유 |
|---|---|
| 그래프 2개로 분리 | 분석은 한 번, 면접은 여러 번 멈추고 재개. 실패 범위를 나눔 |
| 채점을 그래프 밖 백그라운드로 | 다음 질문이 채점을 기다리지 않도록 |
| 평가자 3명 + 중앙값 | 한 번의 채점 편차를 줄임 |
| 검증 에이전트는 다른 모델(3.7) | 같은 모델의 같은 실수를 반복하지 않도록 |
| CHRO는 규칙 기반 | 판정 이유를 설명할 수 있고 재현 가능 |
| 자기소개는 합불 미반영 | 회사 관점 피드백과 검증 포인트 추가 용도 |
| 답변 시간만 45분에 합산 | 대기, 준비 시간 때문에 문항이 잘리지 않도록 |
| 1분 초과해도 끊지 않음 | 실제 면접처럼 경고만, 대신 피드백에서 지적 |
| 검증 포인트는 서류 중심 + 자기소개 신규 주장 | 자기소개 내용 전부를 다시 캐묻지 않도록 |
| 질문 검증 실패 시 원본 문항 | 잘못된 개인화보다 검증된 원본이 안전 |
