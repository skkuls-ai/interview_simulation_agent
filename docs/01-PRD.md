# ProofInterview 기획서 (PRD)

> 한 줄 요약: 지원자의 서류 4종을 분석해 질문 5개짜리 모의 면접을 진행하고, 답변 인용을 근거로 한 피드백을 주는 웹서비스의 1차 MVP 범위를 정한다.
> 기준: 2026-10-01 구현 기준 (원본: Claude Docs 2026-09-29 버전)
>
> 구현 반영: 본문의 「미정」·「(제안)」은 기획 단계 표시다. 구현에서 해결·채택된 내용은 각 문서의 「결정 결과」 절과 [docs/README.md](README.md)의 구현 현황이 우선한다.
> 표기: **확정** = 사용자가 정한 것, **(제안)** = 빈칸을 메우려 임시로 넣은 것, **미정** = 킥오프에서 결정

## 1. 배경과 문제

- 지원자는 예상 질문 목록은 구하지만, 자기 이력서·자소서에서 출발하는 질문에 구체적으로 답하는 연습은 혼자 하기 어렵다.
- 범용 LLM 면접 연습은 개인화가 약하고, 평가가 어느 답변에서 나왔는지 근거가 없거나 답변에 없는 문장을 인용하는 문제가 있다.
- ProofInterview의 메시지: **내 지원서류를 파고드는 면접관, 근거로 설명하는 평가**.

## 2. 목표와 비목표

| 구분 | 내용 |
| --- | --- |
| 목표 | 서류 4종에서 요구사항·주장·검증 포인트를 뽑아 개인화된 질문 5개를 만든다 |
| 목표 | 실제 면접처럼 음성 질문 → 음성 답변(마이크·카메라)으로 진행한다 |
| 목표 | 모든 피드백 판정은 실제 답변 인용과 이유를 함께 보여주고, 인용은 코드가 원문 존재 여부를 검사한다 |
| 목표 | 고정 데모 샘플로 화면 1 → 7을 끊김 없이 완주한다 |
| 비목표 | 합격 예측, 채용 점수 산출, 감정·성격·외모 판단 |
| 비목표 | 카메라 지표를 점수·판정에 반영 (참고 측정값으로만 표시) |
| 비목표 | 실시간 자막, Live 스트리밍 STT (2차 과제도 아님, 확정) |
| 비목표 | 로그인·회원 관리, 직무 2개 이상, 영상 서버 저장 |

## 3. 대상 사용자

- **신입 AI Agent·LLM 애플리케이션 엔지니어 지원자** (확정). 이력서·자소서는 있으나 프로젝트와 기술을 면접에서 구체적으로 설명하기 어려워하는 사람.
- 직무를 하나로 제한하는 이유(PLAN.md 참고): 팀이 질문 은행과 평가 기준을 직접 검수할 수 있는 범위로 통제하기 위해.

## 4. 핵심 기능

화면 흐름은 [docs/02-screen-flow.md](02-screen-flow.md), 동작 규칙은 [docs/03-functional-spec.md](03-functional-spec.md)를 본다.

### Must

| 영역 | 내용 |
| --- | --- |
| 서류 입력 | 이력서·채용공고(인재상 포함)·직무기술서·자소서 4종 모두 필수, 개인정보 동의. 파일(PDF·DOCX·TXT) 또는 텍스트 직접 입력 |
| 서류 분석 | 요구사항(RQ-)·주장(CL-)·검증 포인트(CP-) 추출, 요구사항–경험 연결. 단계별 진행 표시(20~40초) |
| 질문 | 5개 고정 순서(Q-1 자기소개, Q-2·Q-3 인성, Q-4·Q-5 기술), 면접관 1명, 아이스브레이킹 없음 |
| 면접 진행 | 질문 음성 재생 → 5초 대기 → 녹음(최대 1분 30초). 초과 시 면접관 멘트 후 자동 다음 질문. 「답변 완료」는 즉시 다음 질문 |
| 장치 | 마이크·카메라 둘 다 통과해야 면접 시작 |
| 음성 변환 | 서버 STT(답변 종료 후 파일 변환), 변환 후 음성 삭제, 실시간 자막 없음 |
| 피드백 | 태도(말투·시선처리·시간 초과: 측정값 + AI 조언, 점수 없음), 직무 적합성, 답변 일관성(둘 다 판정 라벨 + 인용 + 이유) |
| 질문별 상세 | 질문 원문, 내 답변, 피드백, 연결 정보(서류 주장·확인 포인트) |
| 종료 | 「다시 연습하기」「처음으로」 |
| 품질 관문 | 인용 코드 검증, 질문 코드 검증 |

### Should

- 태도 피드백의 분당 단어 수(말 속도), 군말 횟수 (확정)
- 기술·인성 질문 은행 각 10개를 팀이 검수 (담당표 기준)

### Won't (1차)

- 꼬리질문 (2차, 시간이 되면)
- 새로고침 후 이어하기 (MVP 이후 추가 기능)
- 별도 검증 포인트 지도 화면 (질문별 상세의 연결 정보로 통합, 확정)
- 텍스트 답변 입력 대체, 면접관 2인 패널

## 5. 범위

| | 1차 MVP | 이후 |
| --- | --- | --- |
| 흐름 | 7개 화면 한 방향, 세션은 메모리 저장 | 이어하기, 세션 영속 저장 |
| 질문 | 고정 5개, 꼬리질문 없음 | 꼬리질문(2차) |
| 피드백 | 3영역 + 질문별 상세 | 근거 강화 모드 등 (PLAN.md 참고, Docs 미확정) |

## 6. 성공 기준 (수요일 저녁 MVP 완료 기준)

- [ ] 고정 샘플로 화면 1 → 7이 끊김 없이 완주한다 (마이크 녹음 사용)
- [ ] 서류 4종에서 요구사항·주장·검증 포인트가 실제 LLM으로 생성된다
- [ ] 질문 5개가 고정 순서(자기소개 1, 인성 2, 기술 2)로 나온다
- [ ] 질문마다 음성 → 5초 → 녹음이 동작하고 1분 30초 초과 시 멘트 후 넘어간다
- [ ] 녹음이 서버 STT로 변환되고 변환 후 음성 파일이 삭제된다
- [ ] 피드백 3영역과 질문별 상세가 나오고 인용이 전부 실제 답변에 있다

일정·담당은 [docs/06-wbs-schedule.md](06-wbs-schedule.md), 테스트는 [docs/08-test-scenarios.md](08-test-scenarios.md).

## 7. 원칙 (제품 제약)

- 면접 전·중에는 질문 내용·검증 포인트·평가 기준을 노출하지 않는다 (로딩 화면, 진행 중 API 응답 포함). 면접 중에는 점수·피드백을 보여주지 않는다.
- 카메라 지표(정면 유지 비율·이탈 횟수)는 점수·판정에 쓰지 않는 참고 측정값이다. 영상은 서버로 보내지 않는다.
- 합격 예측·채용 점수 같은 판정성 표현은 쓰지 않는다.
- 코드로 계산 가능한 값(답변 시간, 분당 단어 수, 군말 횟수, 인용 위치)은 LLM에 시키지 않는다.

## 8. 리스크와 가정

| 항목 | 내용 | 대응 |
| --- | --- | --- |
| 가정 | LLM·STT는 학교 GCP Vertex AI 사용을 가정 (모델·호출 한도 미확인) | 킥오프에서 콘솔 확인 |
| 가정 | 프런트는 React + Vite 가정 | 킥오프에서 확정 |
| 리스크 | STT 오인식·무음 → 질문이 판정에서 빠짐 | 「답변 인식 안 됨」 기록 후 진행 (제안) |
| 리스크 | 카메라 측정이 조명·자세에 흔들림 | 「측정 불가」 표시, 점수 미반영 |
| 리스크 | LLM 출력 실패 | Pydantic 구조화 출력, 1회 재시도 후 노드별 fallback |
| 리스크 | 서버 재시작 시 세션 소실 | 허용 (메모리 세션) |
| 리스크 | 3일 일정에 5인 병행 개발 | State·API·mock JSON을 먼저 고정하고 `docs/04-api-schema.md`를 계약으로 사용 |

## 9. 결정 결과 (킥오프 미정 항목)

| 항목 | 결과 |
| --- | --- |
| 담당 | A 예원(서류 입력·분석), B 경빈(질문), C 형석(세션·통합), D 도연(면접 화면·전체 UI), E 지승(피드백). PM 지정은 문서에 기록 없음(미확인) |
| 질문 음성(TTS) | 브라우저 `speechSynthesis`(프런트). 서버 TTS 없음, **API 4개 유지** |
| LLM·STT | Gemini(기본 `gemini-3.8-flash`). 음성 변환도 Gemini 오디오 입력. 연결은 Vertex AI 또는 API 키(AI Studio). 개발 중에는 개인 API 키로 실행했고, 학교 Vertex의 호출 한도는 미확인 |
| 프런트 스택 | React + Vite + TypeScript (확정) |
| 고정 데모 지원자 | 지원자A (`shared/mock/sample_inputs.json`) |
| 저장소 | `skkuls-ai/interview_simulation_agent`, 기본 브랜치 `dev`. 무료 플랜이라 main 보호 규칙은 걸지 못함 |
| 영역 판정 집계 | E의 평가 노드가 LLM 판정을 내고 코드 규칙으로 보정(인식된 답변 2개 미만이거나 근거 없는 판정은 `WITHHELD`) |
| 판정 라벨 | 충분 / 보완 필요 / 미흡 / 판단 보류 (`SUFFICIENT` / `NEEDS_WORK` / `INSUFFICIENT` / `WITHHELD`) 구현 확정 |
